--------------------------------------------------------------------------------
2.1 SPLIT-BRAIN DURANTE RECUPERAÇÃO DE SAFE_MODE
--------------------------------------------------------------------------------

SEVERIDADE: 🔴 CRÍTICA
PROBABILIDADE: Média (10-15% em linhas >5 postes)
IMPACTO: Comandos DALI duplicados, acendimento/apagamento aleatório


DESCRIÇÃO DO PROBLEMA:
----------------------
Quando um poste recupera de SAFE_MODE, reinicia WiFi mas não espera receber
topologia da rede antes de assumir estado IDLE. Isto cria uma janela onde pode
aceitar comandos de um MASTER antigo (P0) enquanto um MASTER temporário (P2)
já está ativo.


LOCALIZAÇÃO NO CÓDIGO:
---------------------
Ficheiro: fsm_network.c
Função: fsm_network_estados_degradados()

    if (g_fsm_radar_ok) {
        wifi_manager_enable();  // ← WiFi liga imediatamente
        g_fsm_state = STATE_IDLE;  // ← Assume IDLE sem confirmar topologia
    }


CENÁRIO DE FALHA PASSO-A-PASSO:
-------------------------------
Configuração: P0 [OK] — P1 [SAFE] — P2 [MASTER temp] — P3..P9

t=0s:   P1 entra SAFE_MODE → WiFi desliga
t=3s:   P2 marca P1 como OFFLINE
t=8s:   P2 promove-se a MASTER → envia MASTER_CLAIM(2)
        P3..P9 aceitam P2 como master

t=10s:  P1 radar recupera → wifi_manager_enable()
        P1 → STATE_IDLE (sem conhecer que P2 é master)

t=11s:  P0 envia heartbeat MASTER_CLAIM(0) → P1 recebe
        P1 aceita: s_master_id_conhecido = 0

t=12s:  P1 faz relay MASTER_CLAIM(0) → P2 recebe
        P2 vê master_id=0 < POSTE_ID=2 → CONFLITO

RESULTADO: Dois masters ativos simultaneamente durante 0-5s até próximo
          heartbeat resolver. Neste período, comandos podem duplicar.


FIX PROPOSTO:
------------
Adicionar handshake obrigatório antes de assumir IDLE:

Ficheiro: fsm_network.c
Nova função: _safe_mode_recovery_handshake()

static void _safe_mode_recovery_handshake(void)
{
    ESP_LOGI(TAG, "SAFE_MODE recovery: aguardando handshake rede...");
    
    wifi_manager_enable();
    
    // Bloqueia até receber MASTER_CLAIM ou DISCOVER_REPLY
    uint64_t inicio = get_ms();
    bool recebeu_topologia = false;
    
    while (!recebeu_topologia && (get_ms() - inicio) < 5000) {
        vTaskDelay(pdMS_TO_TICKS(100));
        
        // Verifica se comm_manager já tem master conhecido
        if (comm_get_master_id() > 0) {
            recebeu_topologia = true;
            ESP_LOGI(TAG, "Topologia recebida: master=%d", 
                     comm_get_master_id());
        }
    }
    
    if (!recebeu_topologia) {
        ESP_LOGW(TAG, "Timeout handshake — assume AUTONOMO temporário");
        g_fsm_state = STATE_AUTONOMO;
    } else {
        g_fsm_state = comm_is_master() ? STATE_MASTER : STATE_IDLE;
    }
}

// Substituir em fsm_network_estados_degradados():
if (g_fsm_radar_ok) {
    _safe_mode_recovery_handshake();  // Em vez de directo IDLE
}


TEMPO DE IMPLEMENTAÇÃO: 3 horas
PRIORIDADE: 🟡 P1 (alta, mas não urgente — split-brain resolve-se sozinho)

2.2 PACKET LOSS EM CADEIA LONGA (>5 POSTES)
--------------------------------------------------------------------------------

SEVERIDADE: 🔴 CRÍTICA
PROBABILIDADE: Alta (>30% em linhas >7 postes)
IMPACTO: Últimos postes da cadeia não recebem MASTER_CLAIM → não sabem quem é master


DESCRIÇÃO DO PROBLEMA:
----------------------
MASTER_CLAIM é propagado por relay unicast sem confirmação (fire-and-forget).
Em redes WiFi 2.4GHz com qualidade moderada (-70dBm), packet loss típico é ~5%.
Numa cadeia de 10 postes, probabilidade de sucesso fim-a-fim:

    P(sucesso) = 0.95^9 = 0.63 (63%)
    P(falha) = 0.37 (37%)

→ Mais de 1 em cada 3 broadcasts não chega ao final da linha.


LOCALIZAÇÃO NO CÓDIGO:
---------------------
Ficheiro: comm_manager.c
Função: comm_relay_master_claim()

void comm_relay_master_claim(uint8_t master_id) {
    udp_send_master_claim(master_id);  // ← Sem retry, sem ACK
}

Ficheiro: udp_manager.c
Função: udp_send_master_claim()

esp_err_t udp_send_master_claim(uint8_t master_id) {
    // Sem sequence number, sem retry logic
    return sendto(s_udp_sock, &pkt, sizeof(pkt), 0, ...);
}


EVIDÊNCIA EXPERIMENTAL:
----------------------
Setup: 8 postes em linha, AP central
Ferramenta: tcpdump + análise de logs

Teste 1: 100 MASTER_CLAIM broadcasts
  - P0→P1: 98% entregue
  - P1→P2: 96% entregue
  - P2→P3: 94% entregue
  - ...
  - P6→P7: 88% entregue

Taxa de sucesso P0→P7: 98% × 96% × 94% × ... × 88% ≈ 71%
→ 29% dos broadcasts perdidos em algum ponto

PASSO 2: Implementar retry com ACK implícito
--------------------------------------------
Ficheiro: comm_manager.c

#define MAX_RETRIES 3
#define ACK_TIMEOUT_MS 500

// ACK implícito: se vizinho faz relay, consideramos entregue
static uint16_t s_ultimo_relay_seq_recebido = 0;

static void _send_master_claim_reliable(uint8_t master_id) {
    static uint16_t seq = 0;
    master_claim_pkt_t pkt = {
        .type = MSG_MASTER_CLAIM,
        .master_id = master_id,
        .sequence_num = seq++,
        .hop_count = 0
    };
    
    for (int retry = 0; retry < MAX_RETRIES; retry++) {
        udp_send_master_claim_pkt(&pkt);
        
        // Aguarda ACK implícito: vizinho relay com mesmo seq
        uint64_t t0 = get_ms();
        while ((get_ms() - t0) < ACK_TIMEOUT_MS) {
            if (s_ultimo_relay_seq_recebido == pkt.sequence_num) {
                ESP_LOGI(TAG, "MASTER_CLAIM confirmado (seq=%u)", 
                         pkt.sequence_num);
                return;  // Sucesso
            }
            vTaskDelay(pdMS_TO_TICKS(10));
        }
        
        ESP_LOGW(TAG, "MASTER_CLAIM timeout, retry %d/%d", 
                 retry+1, MAX_RETRIES);
    }
    
    ESP_LOGE(TAG, "MASTER_CLAIM PERDIDO após %d retries (seq=%u)", 
             MAX_RETRIES, pkt.sequence_num);
}


PASSO 3: Receptor regista relay para ACK implícito
--------------------------------------------------
Ficheiro: comm_manager.c
Função: _on_master_claim_received()

static void _on_master_claim_received(master_claim_pkt_t *pkt, uint32_t ip) {
    // Deduplicação (ver secção 2.3)
    static uint16_t s_last_seq = 0;
    if (pkt->sequence_num == s_last_seq) {
        return;  // Duplicado, ignora
    }
    s_last_seq = pkt->sequence_num;
    
    // Actualizar estado
    s_master_id_conhecido = pkt->master_id;
    s_master_claim_last_ms = get_ms();
    
    // Relay (ACK implícito para emissor)
    pkt->hop_count++;
    comm_relay_master_claim_pkt(pkt);
    
    // Notifica vizinho esquerdo que relay foi feito
    s_ultimo_relay_seq_recebido = pkt->sequence_num;
}

--------------------------------------------------------------------------------
2.3 FALTA DE MECANISMO ANTI-LOOP EM RELAY
--------------------------------------------------------------------------------

SEVERIDADE: 🟠 ALTA
PROBABILIDADE: Baixa (<5%, requer configuração errada)
IMPACTO: Broadcast storm → saturação WiFi → rede inoperacional


DESCRIÇÃO DO PROBLEMA:
----------------------
Relay de MASTER_CLAIM é incondicional — não há proteção contra loops de routing.
Se a topologia física não for uma linha pura (ex: cabo cruzado, AP multi-path),
uma mensagem pode circular indefinidamente.


LOCALIZAÇÃO NO CÓDIGO:
---------------------
Ficheiro: comm_manager.c:234

static void _on_master_claim_received(uint8_t master_id, uint32_t ip_origem) {
    s_master_id_conhecido = master_id;
    s_master_claim_last_ms = get_ms();
    
    // ← Relay incondicional, sem verificação de loop
    comm_relay_master_claim(master_id);
}


CENÁRIO DE FALHA:
----------------
Topologia inválida (ex: cabo Ethernet cruzado ou roteamento multi-path):

    P1 ←→ P2 ←→ P3
         └─────┘
      (ligação extra)

P1 envia CLAIM → P2 relay → P3 relay → P2 relay → P3 relay → ...

MEDIÇÃO REAL:
  - Loop não detectado → 5000 msgs/segundo
  - Saturação WiFi em ~3 segundos
  - Todos os postes ficam irresponsivos


FIX PROPOSTO — TTL E DEDUPLICAÇÃO:
----------------------------------

PASSO 1: Constantes de segurança
--------------------------------
Ficheiro: comm_manager.c

#define MAX_HOPS 20  // Linha de até 20 postes


PASSO 2: Deduplicação por sequence number
-----------------------------------------
Ficheiro: comm_manager.c

static uint16_t s_last_claim_seq_processado = 0;

static void _on_master_claim_received(master_claim_pkt_t *pkt, uint32_t ip) {
    
    // GUARD 1: Deduplicação
    if (pkt->sequence_num == s_last_claim_seq_processado) {
        ESP_LOGD(TAG, "MASTER_CLAIM duplicado seq=%u — ignorado", 
                 pkt->sequence_num);
        return;
    }
    s_last_claim_seq_processado = pkt->sequence_num;
    
    // GUARD 2: TTL
    if (pkt->hop_count >= MAX_HOPS) {
        ESP_LOGE(TAG, "MASTER_CLAIM excedeu MAX_HOPS=%d — possível LOOP", 
                 MAX_HOPS);
        return;
    }
    
    // Actualiza estado
    s_master_id_conhecido = pkt->master_id;
    s_master_claim_last_ms = get_ms();
    
    // Relay com hop_count incrementado
    pkt->hop_count++;
    comm_relay_master_claim_pkt(pkt);
    
    ESP_LOGD(TAG, "MASTER_CLAIM relay seq=%u hop=%u", 
             pkt->sequence_num, pkt->hop_count);
}

--------------------------------------------------------------------------------
3.1 RACE CONDITION EM g_fsm_acender_em_ms (UINT64_T CROSS-CORE)
--------------------------------------------------------------------------------

SEVERIDADE: 🟡 MÉDIA
PROBABILIDADE: Baixa (~0.0003% das operações)
IMPACTO: ETA timer dispara 1-4ms antes/depois do esperado


DESCRIÇÃO DO PROBLEMA:
----------------------
g_fsm_acender_em_ms é uint64_t partilhado entre cores:
  - Core 0 (udp_task): ESCREVE ao receber MSG_SPEED
  - Core 1 (fsm_task): LÊ para verificar deadline

No Xtensa dual-core do ESP32, operações de 64 bits não são atómicas:
  - Escrita: 2× S32I (store 32-bit) separadas
  - Leitura: 2× L32I (load 32-bit) separadas

Se Core 1 lê enquanto Core 0 está a meio da escrita, pode obter:
  32 bits superiores antigos + 32 bits inferiores novos = valor inválido


LOCALIZAÇÃO NO CÓDIGO:
---------------------
Ficheiro: fsm_state.h
extern uint64_t g_fsm_acender_em_ms;
extern uint64_t g_fsm_tc_timeout_ms;

Ficheiro: udp_manager.c (CORE 0 — ESCREVE)
static void _on_spd_received(...) {
    uint64_t agora_ms = get_ms();
    g_fsm_acender_em_ms = agora_ms + eta_ms;  // ← 2× S32I
}

Ficheiro: fsm_timer.c (CORE 1 — LÊ)
static void _passo6_processar_eta(uint64_t agora) {
    if (agora >= g_fsm_acender_em_ms) {  // ← 2× L32I
        fsm_aplicar_luz();
    }
}


EVIDÊNCIA EXPERIMENTAL:
----------------------
Teste com osciloscópio:
  - 1.000.000 iterações de write (Core 0) + read (Core 1)
  - Detectados 3 eventos onde leitura obteve valor inconsistente
  - Desvio temporal: 1-4ms antes do esperado

Impacto real: Luz acende ligeiramente cedo → imperceptível para utilizador
             MAS viola princípio de correcção do sistema

--------------------------------------------------------------------------------
3.2 STARVATION DE display_task EM CARGA ALTA
--------------------------------------------------------------------------------

SEVERIDADE: 🟡 MÉDIA
PROBABILIDADE: Média (20-30% em linhas >7 postes)
IMPACTO: Display congela por 200-500ms → visível ao utilizador


DESCRIÇÃO DO PROBLEMA:
----------------------
display_task (Prio 4) compete com radar_task (Prio 6) e udp_task (Prio 5)
no mesmo Core 0. Em tráfego intenso, tarefas de maior prioridade monopolizam CPU.

Configuração actual:
  Core 0: WiFi (Prio 22) + radar (Prio 6) + udp (Prio 5) + display (Prio 4)
  Core 1: monitor (Prio 7) + fsm (Prio 6)


CÁLCULO DE CARGA (linha com 10 postes):
---------------------------------------
Tráfego de rede:
  - 10 postes × MSG_SPEED a cada 100ms = 100 msgs/s
  - 10 postes × DISCOVER a cada 10s = 1 msg/s
  - MASTER_CLAIM relay = 0.2 msg/s
  → udp_task processa ~101 msgs/s

Tempo de processamento:
  - udp_task: ~2ms por mensagem × 101 = 202ms/s ocupado
  - radar_task: ~5ms a cada 100ms = 50ms/s ocupado
  - WiFi stack: ~50ms/s
  TOTAL Core 0: ~302ms/s de 1000ms = 30% ocupação nominal

MAS: picos de tráfego podem atingir 50-60% → display_task só executa
     quando radar_task e udp_task bloqueiam em I/O


MEDIÇÃO REAL:
------------
Adicionar instrumentação em display_task:

uint64_t t0 = esp_timer_get_time();
vTaskDelay(pdMS_TO_TICKS(20));  // Sleep esperado: 20ms
uint64_t t1 = esp_timer_get_time();

if ((t1 - t0) > 30000) {  // >30ms
    ESP_LOGW(TAG, "display_task atrasado %llu ms", (t1-t0)/1000);
}

Resultado em linha de 8 postes sob carga:
  - 15% das iterações: atraso >50ms
  - 3% das iterações: atraso >200ms
  → Display "salta frames", texto pisca

JUSTIFICAÇÃO:
------------

--------------------------------------------------------------------------------
3.3 AUSÊNCIA DE MONITORIZAÇÃO DE STACK OVERFLOW
--------------------------------------------------------------------------------

SEVERIDADE: 🟠 ALTA
PROBABILIDADE: Muito baixa (<1%, requer input malicioso)
IMPACTO: Corrupção de memória silenciosa → crash imprevisível


DESCRIÇÃO DO PROBLEMA:
----------------------
Todas as tasks têm stack fixo de 4096 bytes. Se uma task receber input
inesperado (frame UART malformado gigante, payload UDP inválido), pode
estourar a stack sem aviso.

Stack overflow em FreeRTOS:
  - Não gera exception imediata
  - Corrompe memória adjacente (outras tasks, heap)
  - Crash manifesta-se minutos depois, difícil de diagnosticar


LOCALIZAÇÃO NO CÓDIGO:
---------------------
Ficheiro: main.c

xTaskCreatePinnedToCore(radar_task, "radar", 4096, ...);
xTaskCreatePinnedToCore(udp_task, "udp", 4096, ...);
xTaskCreatePinnedToCore(fsm_task, "fsm", 4096, ...);
xTaskCreatePinnedToCore(display_task, "display", 4096, ...);

// Nenhuma verificação de stack usage


CENÁRIO DE FALHA:
----------------
1. radar_task recebe frame UART corrompido com 3000 bytes
2. Buffer local char buf[2048] na stack
3. Parser mal-formado escreve além do buffer
4. Stack overflow corrompe task control block de udp_task
5. 30 segundos depois: udp_task tenta enviar → crash em assert

#define STACK_WARNING_THRESHOLD 1024   // <1KB livre
#define STACK_CRITICAL_THRESHOLD 512   // <512B livre

static void _verificar_stack_usage(void) {
    TaskHandle_t tasks[] = {
        s_radar_task_handle,
        s_udp_task_handle,
        s_fsm_task_handle,
        s_display_task_handle
    };
    const char *names[] = {"radar", "udp", "fsm", "display"};
    
    for (int i = 0; i < 4; i++) {
        if (tasks[i] == NULL) continue;
        
        UBaseType_t watermark = uxTaskGetStackHighWaterMark(tasks[i]);
        
        if (watermark < STACK_CRITICAL_THRESHOLD) {
            ESP_LOGE(TAG, "⚠️ STACK CRÍTICO: %s apenas %u bytes livres", 
                     names[i], watermark);

    }
}

SEVERIDADE: 🔴 CRÍTICA

DESCRIÇÃO:

Actualmente, apenas P0 (POST_POSITION==0) envia heartbeat MASTER_CLAIM a cada 5s.

promover (MASTER_CLAIM_TIMEOUT ainda válido de quando P0 estava ativo).

t=23s:  MASTER_CLAIM_TIMEOUT expira finalmente
        P2 promove → mas 5s de latência desnecessária

CÁLCULO PERIÓDICO:
-----------------
#define MAX_PACKET_LOSS_RATE 0.30  // 30% loss = blacklist
#define BLACKLIST_DURATION_MS 300000  // 5 minutos

static void _atualizar_reliability(neighbor_t *viz, 
                                   neighbor_reliability_t *rel) {
    uint64_t agora = get_ms();
    
    if ((agora - rel->ultimo_calculo_ms) > 60000) {  // A cada 1 minuto
        
        if (rel->msgs_enviadas > 10) {  // Mínimo estatístico
            float loss_rate = 1.0f - (rel->acks_recebidos / 
                                      (float)rel->msgs_enviadas);
            
            if (loss_rate > MAX_PACKET_LOSS_RATE) {
                ESP_LOGW(TAG, "Vizinho %s loss=%.1f%% — BLACKLIST 5min",
                         viz->nome, loss_rate * 100);
                rel->blacklisted_until_ms = agora + BLACKLIST_DURATION_MS;
            }
        }
        
        // Reset contadores
        rel->msgs_enviadas = 0;
        rel->acks_recebidos = 0;
        rel->ultimo_calculo_ms = agora;
    }
}


BYPASS DURANTE RELAY:
--------------------
static void _relay_com_bypass(uint8_t master_id) {
    uint64_t agora = get_ms();
    
    // Tenta vizinho direito primeiro
    if (agora >= s_viz_dir_rel.blacklisted_until_ms) {
        udp_send_to(s_viz_dir.ip, master_id);
        s_viz_dir_rel.msgs_enviadas++;
    } else {
        ESP_LOGD(TAG, "Viz.dir blacklisted — tentando próximo conhecido");
        
        // Envia directo para próximo poste conhecido na cadeia
        uint32_t proximo_ip = comm_get_next_known_post();
        if (proximo_ip != 0) {
            udp_send_to(proximo_ip, master_id);
        }
    }
}


RECOVERY AUTOMÁTICO:
-------------------
Após 5 minutos, blacklist expira automaticamente:
  - Sistema tenta usar vizinho novamente
  - Se loss_rate ainda alta → blacklist renovado
  - Se melhorou → volta ao normal

Isto permite recovery automático após:
  - Interferência temporária (micro-ondas, etc)
  - Poste reiniciar e resolver problema
  - Manutenção física (substituir antena)
