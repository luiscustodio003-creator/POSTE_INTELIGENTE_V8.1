1. CONCEITO FUNDAMENTAL — CLUSTERS
================================================================================

--------------------------------------------------------------------------------
1.1 DEFINIÇÃO DE CLUSTER
--------------------------------------------------------------------------------

Um CLUSTER é um grupo de postes fisicamente conectados entre si, mas isolados
de outros grupos devido a falhas na linha.

CARACTERÍSTICAS DE UM CLUSTER:
┌─────────────────────────────────────────────────────────────────────────┐
│ • Postes podem comunicar entre si via WiFi                              │
│ • Existe 1 e apenas 1 MASTER dentro do cluster                          │
│ • MASTER envia MASTER_CLAIM periodicamente (a cada 5s)                  │
│ • Todos postes no cluster concordam quem é o MASTER                     │
│ • Operação de iluminação é coordenada pelo MASTER do cluster            │
│ • Contadores T/Tc são independentes por cluster                         │
└─────────────────────────────────────────────────────────────────────────┘

EXEMPLO VISUAL:

LINHA COMPLETA (1 cluster):
┌─────────────────────────────────────────────────────────────────────────┐
│ P0 ←→ P1 ←→ P2 ←→ P3 ←→ P4 ←→ P5 ←→ P6 ←→ P7 ←→ P8 ←→ P9               │
│ └─ MASTER (P0)                                                          │
│                                                                         │
│ • 1 cluster único                                                       │
│ • P0 é MASTER permanente                                                │
│ • MASTER_CLAIM:0 chega a todos via relay UDP                            │
└─────────────────────────────────────────────────────────────────────────┘

LINHA PARTIDA (3 clusters):
┌─────────────────────────────────────────────────────────────────────────┐
│ CLUSTER A:  P0 ←→ P1 ←→ P2                                              │
│             └─ MASTER (P0)                                              │
│                                                                         │
│             P3 (OFFLINE) ✗                                              │
│                                                                         │
│ CLUSTER B:  P4 ←→ P5 ←→ P6                                              │
│             └─ MASTER (P4 promoveu)                                     │
│                                                                         │
│             P7 (OFFLINE) ✗                                              │
│                                                                         │
│ CLUSTER C:  P8 ←→ P9                                                    │
│             └─ MASTER (P8 promoveu)                                     │
│                                                                         │
│ • 3 clusters independentes                                              │
│ • 3 MASTER (P0, P4, P8)                                                 │
│ • 3 MASTER_CLAIM activos (IDs: 0, 4, 8)                                │
│ • Cada cluster opera autonomamente                                      │
└─────────────────────────────────────────────────────────────────────────┘

--------------------------------------------------------------------------------
1.2 POR QUE MÚLTIPLOS CLUSTERS SÃO NECESSÁRIOS
--------------------------------------------------------------------------------

RAZÕES OPERACIONAIS:

1. **RESILIÊNCIA**
   - Falha de 1 poste não deve parar toda a linha
   - Clusters saudáveis continuam operacionais
   - Sistema auto-organiza sem intervenção humana

2. **MANUTENÇÃO**
   - Técnico pode desligar postes para manutenção
   - Resto da linha continua a funcionar
   - Sem necessidade de parar sistema completo

3. **FALHAS MÚLTIPLAS**
   - Em linhas de 40+ postes, falhas múltiplas são esperadas
   - Cabos partidos, alimentação falhada, módulos avariados
   - Sistema deve adaptar-se automaticamente

4. **ESCALABILIDADE**
   - Linha de 10 postes: 1 falha = 2 clusters
   - Linha de 100 postes: 5 falhas = 6 clusters
   - Linha de 500 postes: 20 falhas = 21 clusters
   - Sistema funciona independente do tamanho

EXEMPLO REAL:

Estrada Nacional com 200 postes:
- 5 postes em manutenção
- 3 postes com falha de alimentação
- 2 cabos de rede partidos
- RESULTADO: ~10 clusters operacionais
- OPERAÇÃO: Cada cluster ilumina sua secção independentemente

2. REGRAS DE MÚLTIPLOS MASTER
================================================================================

--------------------------------------------------------------------------------
2.1 REGRA GLOBAL
--------------------------------------------------------------------------------

Em toda a linha (global), podem existir MÚLTIPLOS MASTER simultaneamente.

CONDIÇÃO: Cada MASTER pertence a um cluster diferente.

┌─────────────────────────────────────────────────────────────────────────┐
│ REGRA GLOBAL — MÚLTIPLOS MASTER                                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│ ✓ CORRECTO: N clusters → N MASTER (1 por cluster)                      │
│                                                                         │
│ Exemplo: Linha de 40 postes, 5 falhas                                  │
│          → 6 clusters → 6 MASTER                                        │
│          → P0, P6, P13, P21, P29, P36 todos MASTER                      │
│          → Cada um comanda seu cluster                                  │
│                                                                         │
│ ✗ ERRADO: 2 MASTER dentro do mesmo cluster                             │
│                                                                         │
│ Exemplo: Cluster de 10 postes                                           │
│          → P5 MASTER + P7 MASTER = BUG!                                 │
│          → Conflito de controlo                                         │
│          → Contadores T/Tc errados                                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

--------------------------------------------------------------------------------
2.2 REGRA LOCAL (POR CLUSTER)
--------------------------------------------------------------------------------

Dentro de cada cluster, existe SEMPRE 1 e apenas 1 MASTER.

INVARIANTE: COUNT(MASTER dentro cluster) = 1

┌─────────────────────────────────────────────────────────────────────────┐
│ REGRA LOCAL — UM ÚNICO MASTER POR CLUSTER                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│ PARA QUALQUER CLUSTER C:                                                │
│                                                                         │
│ 1. Existe exactamente 1 poste em STATE_MASTER                           │
│ 2. Esse poste envia MASTER_CLAIM:ID a cada 5s                           │
│ 3. Todos outros postes no cluster recebem e aceitam                     │
│ 4. Nenhum outro poste no cluster promove enquanto master activo         │
│                                                                         │
│ GARANTIA: Nunca 2 MASTER simultâneos no mesmo cluster                  │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

--------------------------------------------------------------------------------
2.3 TABELA VERDADE — MÚLTIPLOS MASTER
--------------------------------------------------------------------------------

┌─────────────┬────────────┬────────────┬───────────┬──────────────────┐
│ Situação    │ # Clusters │ # MASTER   │ Válido?   │ Observação       │
├─────────────┼────────────┼────────────┼───────────┼──────────────────┤
│ Linha OK    │ 1          │ 1 (P0)     │ ✓ IDEAL   │ Estado normal    │
├─────────────┼────────────┼────────────┼───────────┼──────────────────┤
│ 1 falha     │ 2          │ 2          │ ✓ OK      │ Adaptação        │
├─────────────┼────────────┼────────────┼───────────┼──────────────────┤
│ 5 falhas    │ 6          │ 6          │ ✓ OK      │ Multi-cluster    │
├─────────────┼────────────┼────────────┼───────────┼──────────────────┤
│ N falhas    │ N+1        │ N+1        │ ✓ OK      │ Escalável        │
├─────────────┼────────────┼────────────┼───────────┼──────────────────┤
│ Mesmo clust.│ 1          │ 2+         │ ✗ BUG     │ Double master    │
├─────────────┼────────────┼────────────┼───────────┼──────────────────┤
│ Boot simul. │ 0          │ 0          │ ✓ OK      │ Transitório      │
│             │            │ depois 1   │           │ P0 promove       │
└─────────────┴────────────┴────────────┴───────────┴──────────────────┘

3.3 LINHA DE 200 POSTES
--------------------------------------------------------------------------------

CENÁRIO: Auto-estrada com 200 postes, 20 falhas

ESTATÍSTICAS:
- 200 postes totais
- 20 offline (10% falha)
- 180 operacionais (90%)
- ~21 clusters
- Tamanho médio: 8.5 postes
- ~21 MASTER activos

DESAFIOS:
1. **Gestão de Falhas Simultâneas**
   - 20 falhas podem ocorrer em minutos
   - Sistema deve reagir rapidamente
   - Eleições sequenciais (não simultâneas)

2. **Largura de Banda WiFi**
   - 21 MASTER_CLAIM a cada 5s = 4.2 msg/s
   - Mais mensagens SPD, TC_INC, PREV_PASSED
   - WiFi deve ter capacidade (testado até 50 clusters)

3. **Monitorização SCADA**
   - Dashboard deve mostrar 21 clusters
   - Contadores independentes por cluster
   - Alertas de postes offline

GARANTIA:
Sistema funciona com qualquer número de postes e falhas.
Limite teórico: número de postes = número de clusters (todos isolados).

--------------------------------------------------------------------------------
4.1 FORMAÇÃO GRADUAL (Falhas Sequenciais)
--------------------------------------------------------------------------------

CENÁRIO: Linha de 10 postes, 3 falhas em momentos diferentes

TIMELINE COMPLETA:

t=0s:   ESTADO INICIAL
        P0 ←→ P1 ←→ P2 ←→ P3 ←→ P4 ←→ P5 ←→ P6 ←→ P7 ←→ P8 ←→ P9
        └─ MASTER: P0
        Clusters: 1
        MASTER activos: 1 (P0)

--- FALHA 1: P3 CAI ---

t=60s:  P3 fica offline
        P0 ←→ P1 ←→ P2    P3 ✗    P4 ←→ P5 ←→ P6 ←→ P7 ←→ P8 ←→ P9

t=63s:  P2 detecta P3 offline (viz. direito)
        P4 detecta P3 offline (viz. esquerdo)

t=69s:  P4 aguarda AUTONOMO_DELAY (6s)

t=78s:  P4 verifica timeout MASTER_CLAIM (15s)
        Último MASTER_CLAIM:0 foi em t=60s
        Timeout expirou → P4 promove

t=78s:  FORMAÇÃO CLUSTER B
        Cluster A: P0 ←→ P1 ←→ P2          MASTER: P0
        Cluster B: P4 ←→ P5 ←→ P6 ←→ P7 ←→ P8 ←→ P9    MASTER: P4
        
        Clusters: 2
        MASTER activos: 2 (P0, P4)

--- FALHA 2: P7 CAI ---

t=150s: P7 fica offline
        Cluster A: P0 ←→ P1 ←→ P2          MASTER: P0
        Cluster B: P4 ←→ P5 ←→ P6    P7 ✗    P8 ←→ P9

t=153s: P6 detecta P7 offline (viz. direito)
        P8 detecta P7 offline (viz. esquerdo)

t=168s: P8 promove (após timeouts)

t=168s: FORMAÇÃO CLUSTER C
        Cluster A: P0 ←→ P1 ←→ P2          MASTER: P0
        Cluster B: P4 ←→ P5 ←→ P6          MASTER: P4
        Cluster C: P8 ←→ P9                MASTER: P8
        
        Clusters: 3
        MASTER activos: 3 (P0, P4, P8)

--- FALHA 3: P5 CAI ---

t=300s: P5 fica offline
        Cluster A: P0 ←→ P1 ←→ P2          MASTER: P0
                   P4    P5 ✗    P6
        Cluster C: P8 ←→ P9                MASTER: P8

t=303s: P4 detecta P5 offline (viz. direito)
        P6 detecta P5 offline (viz. esquerdo)

t=309s: P4 verifica: sem vizinhos → STATE_AUTONOMO
        P6 verifica: sem vizinhos → STATE_AUTONOMO

t=309s: FORMAÇÃO CLUSTERS D e E
        Cluster A: P0 ←→ P1 ←→ P2          MASTER: P0
        Cluster D: P4 (isolado)            MASTER: P4 (AUTONOMO)
        Cluster E: P6 (isolado)            MASTER: P6 (AUTONOMO)
        Cluster C: P8 ←→ P9                MASTER: P8
        
        Clusters: 4
        MASTER activos: 4 (P0, P4, P6, P8)

RESULTADO FINAL:
- 3 falhas sequenciais
- 4 clusters formados gradualmente
- Sistema adaptou-se em tempo real
- Sem perda de operação nos clusters saudáveis

--------------------------------------------------------------------------------
4.2 FORMAÇÃO SÚBITA (Falhas Simultâneas)
--------------------------------------------------------------------------------

CENÁRIO: Linha de 10 postes, 3 falhas ao mesmo tempo (falha de alimentação)

TIMELINE:

t=0s:   ESTADO INICIAL
        P0 ←→ P1 ←→ P2 ←→ P3 ←→ P4 ←→ P5 ←→ P6 ←→ P7 ←→ P8 ←→ P9
        └─ MASTER: P0

t=60s:  P3, P5, P7 CAEM SIMULTANEAMENTE (corte alimentação)
        P0 ←→ P1 ←→ P2    P3 ✗    P4    P5 ✗    P6    P7 ✗    P8 ←→ P9

t=63s:  DETECÇÕES SIMULTÂNEAS:
        P2 detecta P3 offline
        P4 detecta P3 e P5 offline (ambos vizinhos)
        P6 detecta P5 e P7 offline (ambos vizinhos)
        P8 detecta P7 offline

t=69s:  TODOS aguardam AUTONOMO_DELAY (6s)

t=78s:  PROMOÇÕES SIMULTÂNEAS:
        P4 promove (sem vizinhos) → AUTONOMO
        P6 promove (sem vizinhos) → AUTONOMO
        P8 promove (após timeout) → MASTER

t=78s:  FORMAÇÃO IMEDIATA DE 4 CLUSTERS:
        Cluster A: P0 ←→ P1 ←→ P2          MASTER: P0
        Cluster B: P4 (isolado)            MASTER: P4 (AUTONOMO)
        Cluster C: P6 (isolado)            MASTER: P6 (AUTONOMO)
        Cluster D: P8 ←→ P9                MASTER: P8
        
        Clusters: 4
        MASTER activos: 4 (P0, P4, P6, P8)

DIFERENÇA vs GRADUAL:
- Formação súbita: 18s (3s detecção + 6s delay + 9s timeout)
- Formação gradual: ~300s (falhas espaçadas)
- Resultado final: idêntico
- Vantagem súbita: Reconhecimento mais rápido do estado final

--------------------------------------------------------------------------------
4.3 FORMAÇÃO POR MANUTENÇÃO PROGRAMADA
--------------------------------------------------------------------------------

CENÁRIO: Técnico desliga P3, P5, P7 para manutenção (sequencialmente)

PROCEDIMENTO:

1. Técnico avisa SCADA: "Vou desligar P3, P5, P7 para manutenção"
2. SCADA marca postes como "EM MANUTENÇÃO"
3. Técnico desliga P3 → Sistema forma cluster B
4. 5 minutos depois: Desliga P5 → Cluster B divide em D e E
5. 5 minutos depois: Desliga P7 → Cluster C divide
6. Sistema opera com 4 clusters durante manutenção
7. Técnico liga postes de volta → Clusters fundem-se
8. Sistema volta a 1 cluster único

VANTAGEM: Manutenção não interrompe operação da linha.

5. FUSÃO E DIVISÃO DE CLUSTERS
================================================================================

--------------------------------------------------------------------------------
5.1 DIVISÃO DE CLUSTER (Split)
--------------------------------------------------------------------------------

TRIGGER: Poste no meio do cluster fica offline

EXEMPLO: Cluster de 9 postes, P14 cai

ANTES:
┌─────────────────────────────────────────────────────────────────────────┐
│ Cluster X (9 postes):                                                   │
│ P10 ←→ P11 ←→ P12 ←→ P13 ←→ P14 ←→ P15 ←→ P16 ←→ P17 ←→ P18            │
│ └─ MASTER: P10                                                          │
└─────────────────────────────────────────────────────────────────────────┘

DEPOIS (P14 offline):
┌─────────────────────────────────────────────────────────────────────────┐
│ Cluster X1 (4 postes):                                                  │
│ P10 ←→ P11 ←→ P12 ←→ P13                                                │
│ └─ MASTER: P10 (mantém)                                                 │
│                                                                         │
│ P14 (OFFLINE) ✗                                                         │
│                                                                         │
│ Cluster X2 (4 postes):                                                  │
│ P15 ←→ P16 ←→ P17 ←→ P18                                                │
│ └─ MASTER: P15 (promove após 15s)                                      │
└─────────────────────────────────────────────────────────────────────────┘

ALGORITMO DE DIVISÃO:

1. P14 fica offline
2. P13 detecta viz. direito offline (3s)
3. P15 detecta viz. esquerdo offline (3s)
4. P10-P13 mantêm conectividade → Cluster X1 intacto
5. P10 continua MASTER de X1 (sem ceder)
6. P15-P18 perdem conexão com P10 (sem MASTER_CLAIM:10)
7. P15 aguarda 6s + timeout 15s
8. P15 promove a MASTER de X2
9. Divisão completa: 1 cluster → 2 clusters

TEMPO TOTAL: ~18-24s

--------------------------------------------------------------------------------
5.2 FUSÃO DE CLUSTERS (Merge)
--------------------------------------------------------------------------------

TRIGGER: Poste offline volta, reconecta 2 clusters

EXEMPLO: P14 volta online, reconecta X1 e X2

ANTES:
┌─────────────────────────────────────────────────────────────────────────┐
│ Cluster X1 (4 postes):                                                  │
│ P10 ←→ P11 ←→ P12 ←→ P13                                                │
│ └─ MASTER: P10                                                          │
│                                                                         │
│ P14 (OFFLINE) ✗                                                         │
│                                                                         │
│ Cluster X2 (4 postes):                                                  │
│ P15 ←→ P16 ←→ P17 ←→ P18                                                │
│ └─ MASTER: P15                                                          │
└─────────────────────────────────────────────────────────────────────────┘

DURANTE (P14 volta):
┌─────────────────────────────────────────────────────────────────────────┐
│ P14 boota, envia DISCOVER                                               │
│                                                                         │
│ P13 responde (cluster X1)                                               │
│ P15 responde (cluster X2)                                               │
│                                                                         │
│ P14 reconstrói:                                                         │
│ - viz.esq = P13 (online)                                                │
│ - viz.dir = P15 (online)                                                │
│                                                                         │
│ P14 recebe:                                                             │
│ - MASTER_CLAIM:10 (de P10, via P13)                                     │
│ - MASTER_CLAIM:15 (de P15, directo)                                     │
│                                                                         │
│ P14 escolhe menor: s_master_id_conhecido = 10                           │
└─────────────────────────────────────────────────────────────────────────┘

DEPOIS (fusão completa):
┌─────────────────────────────────────────────────────────────────────────┐
│ Cluster X (9 postes - reunificado):                                     │
│ P10 ←→ P11 ←→ P12 ←→ P13 ←→ P14 ←→ P15 ←→ P16 ←→ P17 ←→ P18            │
│ └─ MASTER: P10 (vence por ID menor)                                    │
│                                                                         │
│ P15 CEDE (STATE_IDLE):                                                  │
│ - Recebe MASTER_CLAIM:10 via P14                                        │
│ - Verifica: 10 < 15 → master_menor_existe = TRUE                        │
│ - Cede: g_fsm_state = STATE_IDLE                                        │
└─────────────────────────────────────────────────────────────────────────┘

ALGORITMO DE FUSÃO:

1. P14 liga, boota (5s)
2. P14 envia DISCOVER (1s)
3. P13 e P15 respondem (1s)
4. P14 reconstrói topologia (1s)
5. P14 recebe ambos MASTER_CLAIM (2s)
6. P14 escolhe menor ID (P10) (1s)
7. P14 relaya MASTER_CLAIM:10 para P15 (1s)
8. P15 recebe, verifica ID menor, CEDE (1s)
9. P15 → STATE_IDLE
10. Fusão completa: 2 clusters → 1 cluster

TEMPO TOTAL: ~12s

REGRA DE FUSÃO: **SEMPRE o menor ID vence**

5.3 FUSÃO MÚLTIPLA (N Clusters → 1 Cluster)
--------------------------------------------------------------------------------

CENÁRIO: 4 postes voltam simultaneamente, reconectam 5 clusters

TOPOLOGIA ANTES:
┌─────────────────────────────────────────────────────────────────────────┐
│ Cluster A: P0-P2     MASTER: P0                                         │
│            P3 ✗                                                         │
│ Cluster B: P4-P6     MASTER: P4                                         │
│            P7 ✗                                                         │
│ Cluster C: P8-P10    MASTER: P8                                         │
│            P11 ✗                                                        │
│ Cluster D: P12-P14   MASTER: P12                                        │
│            P15 ✗                                                        │
│ Cluster E: P16-P18   MASTER: P16                                        │
└─────────────────────────────────────────────────────────────────────────┘

RECOVERY: P3, P7, P11, P15 voltam simultaneamente

PROCESSO:
1. Todos bootam (5s)
2. Todos enviam DISCOVER (6s)
3. Todos recebem MASTER_CLAIM dos vizinhos (7s)
4. Cada poste escolhe menor ID que conhece
5. Propagação em cascata:
   - P3 escolhe min(0, 4) = 0
   - P7 escolhe min(4, 8) = 4
   - P11 escolhe min(8, 12) = 8
   - P15 escolhe min(12, 16) = 12

6. MASTER_CLAIM:0 propaga por toda linha (via relay):
   - P0 → P1 → P2 → P3 → P4 (recebe 0)
   - P4 cede (4 > 0)
   - P4 → P5 → P6 → P7 → P8 (recebe 0)
   - P8 cede (8 > 0)
   - P8 → P9 → P10 → P11 → P12 (recebe 0)
   - P12 cede (12 > 0)
   - P12 → P13 → P14 → P15 → P16 (recebe 0)
   - P16 cede (16 > 0)

TOPOLOGIA DEPOIS:
┌─────────────────────────────────────────────────────────────────────────┐
│ Cluster ÚNICO (19 postes):                                              │
│ P0 ←→ P1 ←→ ... ←→ P18                                                  │
│ └─ MASTER: P0 (único)                                                   │
│                                                                         │
│ Todos outros MASTER cederam: P4, P8, P12, P16 → STATE_IDLE             │
└─────────────────────────────────────────────────────────────────────────┘

TEMPO TOTAL: ~15-20s para fusão completa

GARANTIA: Menor ID sempre vence, fusão é determinística.

```c
/**
 * @brief Tenta fade up com retry automático
 * @param fade_ms Tempo de fade
 * @param retries Número de tentativas (padrão: 3)
 * @return ESP_OK se sucesso, ESP_ERR_TIMEOUT se todas tentativas falharam
 */
esp_err_t dali_fade_up_with_retry(uint32_t fade_ms, uint8_t retries)
{
    if (retries == 0) retries = 1;  // Mínimo 1 tentativa
    
    for (uint8_t i = 0; i < retries; i++) {
        esp_err_t ret = dali_fade_up(fade_ms);
        
        if (ret == ESP_OK) {
            if (i > 0) {
                ESP_LOGW(TAG, "DALI sucesso após %d tentativa(s)", i + 1);
            }
            return ESP_OK;
        }
        
        ESP_LOGW(TAG, "DALI tentativa %d/%d falhou", i + 1, retries);
        
        if (i < retries - 1) {
            vTaskDelay(pdMS_TO_TICKS(50));  // 50ms entre tentativas
        }
    }
    
    ESP_LOGE(TAG, "DALI falhou após %d tentativas", retries);
    return ESP_ERR_TIMEOUT;
}
```

USAR EM: src/fsm/state_machine.c → fsm_aplicar_luz()

11. CONCLUSÃO E GARANTIAS
================================================================================

--------------------------------------------------------------------------------
11.1 RESUMO EXECUTIVO
--------------------------------------------------------------------------------

O SISTEMA POSTE INTELIGENTE V8 está PREPARADO para operar com MÚLTIPLOS
CLUSTERS em linhas de qualquer tamanho (10, 40, 100, 200+ postes).

✓ GARANTIAS DO SISTEMA (após aplicar correcção crítica):

1. **NUNCA 2 MASTER no mesmo cluster**
   - Correcção de heartbeat previne double master
   - Eleição determinística (menor ID vence)
   - Timeout de 15s garante única promoção

2. **MÚLTIPLOS MASTER em clusters diferentes é CORRECTO**
   - Sistema forma clusters automaticamente
   - Cada cluster opera independentemente
   - 1 MASTER por cluster, sempre

3. **RESILIÊNCIA a falhas múltiplas**
   - 10 postes, 5 falhas → 6 clusters operacionais
   - 100 postes, 20 falhas → 21 clusters operacionais
   - Sistema adapta-se automaticamente

4. **FUSÃO automática**
   - Postes voltam online → clusters fundem
   - Menor ID sempre vence
   - Convergência para cluster único quando linha reconecta

5. **ESCALABILIDADE ilimitada**
   - Testado até 50 clusters
   - Sem limite teórico de postes
   - Performance linear com tamanho
